# The Watch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Nothing slips quietly. The planner says what is going to go wrong while there is still time to do something about it, and places work so the thing due Wednesday lands before Wednesday.

**Architecture:** One pure module, `src/lib/watch.ts`, turns the day's payload, the week's commitments and each task's planning history into at most five sentences. None of it needs new data: `carryOver` has always left the old `daily_plan_entries` row behind, so every day a task was ever planned is already recorded and has simply never been counted. Then `fillWeek` extends the placement the sessions slice built, ordering by whichever date is nearest — due or promised — and refusing to place work after the day it is owed.

**Tech Stack:** Next.js 16 App Router, React 19 (react-compiler lint: no synchronous `setState` in effect bodies), Tailwind 4 Carbon tokens, Drizzle + better-sqlite3, zod 4, Vitest 5 jsdom, `motion` 12.

**Spec:** `docs/superpowers/specs/2026-09-25-reliable-planner-design.md` (§6, §7)

**Depends on:** the honest-forecast slice (drift, working days) and the commitments slice, both merged.

## Global Constraints

- Carbon tokens only — `src/test/tokens.test.ts` bans `ink`, `slate`, `brass`, `paper`, `tone=`, `on-paper`, `shadow-dock`. Sentence case. `focus-ring` on every interactive element. `aria-label` on icon-only controls.
- No synchronous `setState` in an effect body (react-compiler lint).
- Tests never touch the network, never depend on the real clock, and never depend on the machine's timezone.
- **The horizon is 7 days.** `WATCH_HORIZON_DAYS = 7`, exported. Beyond it is noise.
- **At most five lines.** `WATCH_LIMIT = 5`. Over five, the last reads "and N more". More than five and it becomes a second inbox, which is what every "at risk" panel becomes before people stop reading it.
- **When nothing is at risk it renders nothing at all.** Not "all clear" — nothing. The silence is the signal.
- Thresholds, all exported constants: carried 4 or more times; open 21 days with no run and no session.
- No colour alarm. The sentence is the alarm.

### Task 1: The five rules

**Files:**
- Create: `src/lib/watch.ts`, `src/lib/watch.test.ts`
- Modify: `src/domain/plan/index.ts` (+ test), `src/lib/dto.ts`, `src/lib/planner.ts` (+ test), `src/lib/home.ts` (+ test)

**Interfaces:**
- Consumes: `dueBy` and `currentFor` from `@/domain/commitments`; `driftFactor`/`forecastMinutes` from `@/lib/drift`; `isWorkingDay` from `@/lib/work-hours`; `listPlan` from `@/domain/plan`.
- Produces:
  - `src/domain/plan/index.ts`: `planHistory(db, taskIds: number[]): Map<number, { days: number; firstPlanned: string }>` — from the `daily_plan_entries` rows a task already has, in one grouped query.
  - `src/lib/watch.ts`:
    - `export const WATCH_HORIZON_DAYS = 7;` `export const WATCH_LIMIT = 5;` `export const CARRY_THRESHOLD = 4;` `export const STALE_DAYS = 21;`
    - `export type WatchKind = "due-unbooked" | "promise-unbooked" | "carried" | "stale" | "day-over";`
    - `export interface WatchItem { kind: WatchKind; text: string; taskId?: number; date?: string; }`
    - `watchItems(input: WatchInput): { items: WatchItem[]; more: number }`
  - `src/lib/dto.ts`: `WatchItemDTO`; `PlannerDayDTO.watch`, `HomeDTO.watch`.

- [ ] **Step 2: Run to verify it fails, then write the module**

Ordering, before the cap: anything overdue, then by the date it turns on you, then by kind in the order of the spec's table. A rule with no date sorts after the dated ones.

Each sentence names the thing and says the fact. "Due Thursday, no time set aside". "Promised to Anita for Friday, not planned". "Carried four times". "Open three weeks, never started". "Wednesday is about 2h over". No exclamation, no severity word, no colour.

- [ ] **Step 3: `planHistory`, from data that has always been there**

`carryOver` adds the task to the new day and clears the old day's blocks, but it never deletes the old `daily_plan_entries` row. So the count of rows per task *is* how many days it has been planned, and the earliest `createdAt` is when it first was. One grouped query for a list of ids.

Test it against a task carried across three days, and against one planned on the same day twice (which the unique index prevents, so it stays one).

- [ ] **Step 4: Carry it on the payloads**

`plannerDay` and `homePayload` gain `watch`. Compute it once per request. Home shows only the first line; the planner shows up to five.

Run: `npm test && npx tsc --noEmit && npm run lint`, plus the `TZ` run.

### Task 3: Placement that respects a date

**Files:**
- Modify: `src/lib/scheduler.ts` (+ test), `src/domain/blocks/index.ts` (+ test), `src/lib/validation.ts`, `src/app/api/plan/place/route.ts` (+ test), `src/components/planner/week-view.tsx` (+ test), `README.md`

**Interfaces:**
- Produces: `fillWeek(db, { from, now? }): { placed: number; unfitted: { taskId: number; title: string; minutes: number; by: string }[] }`.

- [ ] **Step 1: Order by the date that is nearest**

`fillDay` currently places in plan order. Order instead by the soonest of the task's due date and its commitment's promised date, undated work last, ties keeping plan order. A test with three tasks added in the reverse of their due order proves it.

- [ ] **Step 2: `fillWeek`**

Walks the working days of the week from `from`, skipping non-working days, placing each task's sessions into the first day with room — and **never after the day it is owed**. Each day's room is `freeMinutes` with `now` **after drift**: a day whose forecast is already full takes nothing more, because placing work a forecast says will not happen is how a plan becomes a fiction.

What will not fit comes back as rows, not as a number: the task, its minutes, and the date it was owed by.

- [ ] **Step 3: Say what did not fit**

The week view gains "Plan the week". Afterwards it says, in words: "Three tasks, about 4h, would not fit before their dates." and lists them. **A planner that silently drops what does not fit is worse than no planner** — that sentence is the feature, and it needs a test that the list is actually rendered and not just counted.

- [ ] **Step 4: README**

A section on the watch and on planning a week: the five things it watches for, the seven-day horizon, the five-line cap, that silence means nothing is wrong, and that planning a week tells you what it could not place rather than dropping it.

Then close the Planner section by tying the three slices together — the forecast makes the numbers true, commitments say who is waiting, and the watch speaks before the date rather than on it.

- [ ] **Step 5: Run the suite and commit**

Run: `npm test && npx tsc --noEmit && npm run lint`, plus the `TZ` run.

```bash
git commit -m "feat(planner): place by the nearest date, plan a week, and say what would not fit

<trailers>"
```
